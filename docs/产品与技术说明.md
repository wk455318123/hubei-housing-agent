# 湖北省保租房智能体｜产品与技术说明

校准日期：2026-08-31

## 1. 产品结论

湖北住房保障不适合做成“一套全省资格 + 一张静态房源表”。省级文件负责制度方向，各市县制定具体实施条件，项目和批次又有独立期限；公租房、保障性租赁住房、人才住房的规则和入口也不同。

正确形态是：

> 省级统一服务入口 + 属地分流器 + 分类型资格预判器 + 项目匹配台 + 房态/入口核验器 + 正式办理连接器。

给领导的简要介绍：**群众先选实际申请城市，再说明就业、住房、预算和通勤需求。系统自动区分公租房、保租房和人才住房，按属地项目规则给出资格预判、项目匹配、待核验材料与官方入口；对历史公告、建设进度和过期批次明确降级，不把它们当成当前房源。这样既减少群众反复问、基层反复解释，也让省市部门看到咨询、需求、房源和办理链路中的堵点。**

## 2. 目标用户与核心任务

| 用户 | 主要困难 | 系统任务 |
|---|---|---|
| 来鄂青年 / 高校毕业生 | 不清楚城市政策和住房类型 | 先定城市、再分流项目 |
| 新市民 / 稳定就业人员 | 无房、就业、社保口径易混 | 按当前项目列出满足项与未知项 |
| 新就业群体 / 基本公共服务人员 | 班次、园区、床位和专项规则复杂 | 匹配通勤并隔离专项规则 |
| 人才及家庭 | 人才认定、单位、住房和补贴叠加复杂 | 路由到属地人才政策和项目入口 |
| 公租房保障家庭 | 资格、补贴、轮候、实物配租混为一谈 | 拆分资格确认与具体配租批次 |
| 政务客服 / 运营人员 | 重复咨询多、旧公告误导风险高 | 提供标准解释、来源和回源动作 |
| 省市管理部门 | 需求、项目、咨询和办理数据割裂 | 形成跨层级但不跨权限的数据视图 |

## 3. 核心问法

1. “我准备在武汉申请，应该先看公租房还是保租房？”
2. “湖北省文件写了新市民，宜昌具体要不要就业证明？”
3. “预算 1800 元，到襄阳高新区 30 分钟内有哪些项目？”
4. “武汉的 85 折是不是湖北所有保租房都一样？”
5. “江汉区 2026 年腾退房源网页还有效，现在能登记吗？”
6. “宜昌屈原东路公告写常态化，现在还有房吗？”
7. “青隽城是人才住房，普通保租房申请人能直接套条件吗？”
8. “新项目、余房或报名截止变化时提醒我。”

## 4. 完整服务链

| 阶段 | 智能体动作 | 输出 | 边界 |
|---|---|---|---|
| 属地识别 | 解析省、市州、县市区/功能区和就业地 | 唯一服务辖区 | 未明确市州时不做资格结论 |
| 产品分流 | 区分公租房、保租房、人才住房 | 候选产品类型 | 名称含“人才/青年”不自动决定类型 |
| 资格预判 | 读取当前属地、项目/批次规则，三值执行 | 可能匹配、暂不匹配、待核验 | 不输出“审核通过” |
| 项目检索 | 按城市、区域、预算和类型检索 | 带来源和状态日期的候选 | 跨城项目不混排 |
| 通勤/预算匹配 | 合规地图 + 租金区间 + 用户偏好排序 | 推荐理由和取舍 | 不把排序当资格或房态判断 |
| 房态与入口核验 | 联合检查规则有效性、实时库存、入口状态 | `current_actionability` | 三者任一缺失即为 false/unknown |
| 订阅提醒 | 订阅新批次、余房、截止日和价格变化 | 最少必要通知 | 单独授权、可退订、不过度提醒 |
| 正式办理连接 | 返回属地白名单入口与材料版本 | 下一步动作 | 不代填、不代提交、不绕过实人认证 |
| 进度协同 | 展示官方系统回传的节点 | 待补件、选房、签约等 | 不暴露底层敏感审核信息 |

## 5. 规则与时效口径

### 5.1 三级证据

| 层级 | 决定什么 | 不得越界 |
|---|---|---|
| `policy_direction` | 省级保障对象大类、供给方向和城市责任 | 不直接推导个人资格、项目租金或当前房态 |
| `local_project_rule` | 市县实施条件、项目/批次准入、租金、材料、流程和期限 | 只用于载明城市、项目、批次、人群与有效期 |
| `current_actionability` | 当前是否有房、是否受理、入口是否有效 | 必须由实时房态、有效规则和有效入口联合生成 |

页面能打开、项目已交付、建设已完工、历史公告写“常态化”或平台仍可登录，都不能单独令 `current_actionability=true`。

### 5.2 产品类型隔离

- `public_rental`：公租房、租赁补贴和实物配租批次分别处理。
- `affordable_rental`：保障性租赁住房，具体准入和租金按城市、项目或批次核验。
- `talent_special_rental`：人才专项租赁住房，人才认定、单位、住房、补贴和入口按属地人才政策执行。

“青年公寓”“人才社区”“先租后售”等是项目名称或子类型，不能替代 `program_type`。

## 6. 数据模型

```text
Jurisdiction
  code, name, level, parent_code, jurisdiction_type, status

SourceDocument
  id, title, issuer, jurisdiction_codes[], program_type,
  temporal_level, source_kind, effective_period, source_url,
  published_at, fetched_at, checksum, review_status

RuleSet
  id, jurisdiction_codes[], program_type, project_id?, batch_id?,
  version, effective_period, predicates[], evidence_spans[], review_status

Project
  id, province_code, prefecture_code, county_code?, functional_zone_code?,
  name, address, program_type, project_subtype, operator,
  rule_set_id?, lifecycle, status_as_of

InventorySnapshot
  id, project_id, batch_id?, snapshot_at, availability_status,
  available_count?, unit_types[], rent_min?, rent_max?, deadline?, source_id

OfficialEntryCheck
  id, jurisdiction_code, project_id?, batch_id?, entry_url,
  entry_type, checked_at, status, redirect_chain[], source_id

ActionabilityDecision
  id, project_id, batch_id?, evaluated_at, current_actionability,
  rule_set_id, inventory_snapshot_id, official_entry_check_id, reasons[]

UserPreference
  session_id, target_prefecture_code, target_county_code?, employment_area?,
  household_housing_state?, talent_state?, benefit_state?, budget_max?,
  commute_max?, consent_scope
```

行政区划必须使用代码作主键，名称仅展示；功能区单独标注 `jurisdiction_type=functional_zone`，不得伪装成行政区县。

## 7. 规则服务

规则主键：

```text
program_type + jurisdiction_code + project_id? + batch_id? + effective_period + version
```

执行顺序：

1. 解析目标市州/县市区，未明确则停止并追问。
2. 识别产品类型；多类型请求并行执行，结果不可互相补条件。
3. 获取当前有效市县及项目/批次规则；只有省级政策时仅做方向解释。
4. 用 `true | false | unknown` 执行资格预判。
5. 用户问“现在能办吗”时，再联合检查库存和入口。

```text
current_actionability = true 当且仅当：
  RuleSet 有效且已复核
  AND InventorySnapshot 在 SLA 内且状态为 available/open
  AND OfficialEntryCheck 为 valid
  AND 三者的辖区、产品、项目和批次一致
```

## 8. 匹配与订阅

```text
hard_gate = 同城 + 产品类型一致 + 有效规则可回源 + 无明确资格冲突
score = 资格线索40% + 通勤25% + 预算20% + 户型10% + 数据新鲜度5%
```

生产“当前找房”只允许 `current_actionability=true`。历史样例进入独立参考区，不得用高匹配分制造“可以申请”的暗示。切换城市时必须清空原城市工作地、区域和订阅条件。

订阅事件包括：`new_project`、`new_batch`、`inventory_available`、`deadline_approaching`、`rent_changed`、`entry_invalidated`。发送前再次计算可办状态；用户可暂停、退订和删除偏好。

## 9. 正式办理路由

| 类型 | 入口策略 | 说明 |
|---|---|---|
| 公租房 | [湖北政务服务网](https://zwfw.hubei.gov.cn/) / 鄂汇办选择属地事项；实物配租再绑定当前批次 | 资格、补贴、轮候和选房分开 |
| 保租房 | 属地住建平台、项目运营主体或当前公告指定入口 | 不假定存在全省统一个人申请深链 |
| 人才住房 | 当前属地人才政策与人才服务平台 | 入口可达不等于符合或有房 |

跳转前展示主体、适用城市/项目/批次、检查时间、截止时间、材料版本和离开提示。

## 10. 原型实现与上线要求

- 纯 HTML/CSS/JavaScript，无构建依赖。
- 页面内置同版兜底数据；外部 JSON 加载失败也不会回退到其他省市内容。
- 只允许 HTTPS、精确官方主机、无账号口令 URL；拦截未知域名和异常查询。
- Demo 不采集手机号、证件号和验证码，不持久化、不发送真实提醒。

上线前必须补齐：

1. 省级统筹并建立各市州数据责任矩阵、规则责任人和刷新 SLA。
2. 与属地住建、人才部门和运营主体接通项目主数据、实时房态、入口状态和批次公告。
3. 建立公租房、保租房、人才住房三套规则库；结构化规则双人复核、可回滚。
4. 使用真实地图、租金和房态替换演示矩阵，展示计算与刷新时间。
5. 完成统一身份认证、最小化采集、授权、留存、删除和日志脱敏评审。
6. 联测跨城串规、跨类型串规、历史“常态化”、建设进度误判、无效外链、重复通知和敏感信息泄漏。
